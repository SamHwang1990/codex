# 核心 Agent 层业务逻辑说明

这份文档只解释 Codex 核心 agent 层的业务逻辑，不做详细代码讲解。你可以把核心 agent 层理解成一个“本地执行的智能工作流引擎”：它接收用户目标，把目标转换成模型可理解的上下文，决定可用能力，驱动模型思考和行动，处理工具副作用与权限风险，持续把进展回传给界面，并把整个过程保存下来，便于恢复、审计、回滚和继续执行。

核心 agent 层主要对应 `codex-rs/core`。上层界面可以是 TUI、`codex exec`、IDE 或 app-server 客户端，但进入核心层后，业务概念基本一致：一个 thread 里有多个 turn，每个 turn 里有用户输入、agent 输出、推理、工具调用、文件变化、审批、错误和最终结果。

## 1. 核心层解决什么问题

核心 agent 层的职责不是“显示界面”，也不是“单纯调用模型”。它承担的是完整 agent 运行闭环：

- 接收用户目标，并把它归入某个会话。
- 读取当前项目、配置、权限、历史、技能、工具和环境。
- 构造模型输入，让模型知道“现在是谁、在哪里、能做什么、不能做什么、已经发生了什么”。
- 接收模型的流式输出。
- 如果模型要调用工具，判断工具是否存在、是否允许、是否需要用户批准。
- 执行工具，并把工具结果反馈给模型。
- 在多轮模型调用和工具调用之间循环，直到 turn 完成、中断、失败或需要用户介入。
- 把所有关键事件通知给上层界面。
- 持久化历史，支持恢复、fork、回滚和审计。

换句话说，核心层是 Codex 的“业务大脑”和“执行调度中心”。

## 2. 关键业务对象

### Thread

Thread 是一段完整会话。用户打开 Codex 开始一个任务，就是启动一个 thread。一个 thread 可以被保存、恢复、fork、归档，也可以有名字、目标、记忆状态和当前配置快照。

业务上，thread 解决的是“这件事从哪里开始、走到哪里、下次如何继续”的问题。

### Turn

Turn 是一次用户输入触发的 agent 工作周期。用户说“修复这个 bug”，这是一个 turn；用户继续说“再加测试”，这是另一个 turn。

一个 turn 不是简单的一问一答。它可能包含：

- 用户输入。
- 模型思考。
- 模型输出给用户的文字。
- 一次或多次工具调用。
- 命令执行结果。
- 文件修改结果。
- 审批请求。
- 错误、重试、中断。
- 最终回答。

业务上，turn 解决的是“这一次用户要求如何被处理完”的问题。

### Item

Item 是 turn 内的原子记录。它可以是用户消息、agent 消息、推理摘要、shell 命令、MCP 工具调用、文件变更、计划、审查结果等。

业务上，item 解决的是“过程如何被看见、保存和恢复”的问题。

### Session

Session 是一个正在运行的 thread 的内存状态。它维护当前 active turn、历史、配置、工具连接、MCP 状态、审批等待项、模型客户端、持久化 writer 等。

业务上，session 解决的是“这个 agent 当前活着时，手里握着哪些状态和资源”的问题。

### Operation 和 Event

核心层使用“输入操作”和“输出事件”的模式：

- Operation 是外部告诉核心层要做什么，例如开始用户 turn、中断、审批通过、刷新 MCP、压缩历史。
- Event 是核心层告诉外部发生了什么，例如 turn started、item started、命令输出、agent message delta、turn completed。

这让核心层可以异步工作：上层发出命令后，不需要阻塞等待最终结果，而是持续接收事件流。

## 3. 一次普通任务的完整流程

下面用通用语言描述用户说“帮我修复这个测试失败”时，核心 agent 层的完整业务流程。

### 3.1 接单

上层界面把用户输入提交给核心层。核心层不会马上直接调用模型，而是先把这次请求包装成一个带唯一 id 的操作。

这个 id 很重要。后续所有事件都可以和这次请求关联起来，例如“哪个 turn 开始了”“哪个命令属于这个 turn”“哪个审批是为了这个操作产生的”。

### 3.2 创建或定位会话

核心层先确认这个请求属于哪个 thread：

- 如果是新会话，创建新的 thread。
- 如果是继续会话，加载已有 thread。
- 如果是 fork，会复制或截取原会话历史形成新 thread。
- 如果是临时会话，可以不落到长期存储。

这一步决定 agent 看到多少历史、在哪个目录工作、使用哪套配置、是否继承之前的 shell 状态或执行策略。

### 3.3 准备 turn

核心层为这次用户输入创建一个 turn 上下文。这个上下文会收集：

- 当前工作目录。
- 模型和 provider。
- 推理强度、摘要策略、输出 schema。
- 审批策略。
- 文件系统和网络权限。
- 当前人格或协作模式。
- 可用执行环境。
- 本轮动态工具。
- 当前 thread 的历史和配置快照。

可以把 turn 上下文理解成“本轮工作的任务包”。模型和工具都围绕这个任务包运行。

### 3.4 判断是新 turn 还是追加输入

如果当前已经有一个可继续的 active turn，核心层可能把用户输入当作“追加指令”送进去。这就是 steer。

如果当前没有 active turn，或者当前 turn 不允许追加，核心层会启动一个新的工作任务。

这解决了用户在 agent 运行中继续打字的问题：有时是补充上下文，有时必须排队到下一轮。

### 3.5 装配上下文

在调用模型前，核心层会把许多信息整理成模型输入：

- 用户刚刚说了什么。
- 之前对话和工具结果中哪些内容仍然重要。
- 当前项目的 AGENTS.md 指令。
- 用户配置和开发者指令。
- 当前操作系统、工作目录、沙箱、审批规则。
- 可用工具清单。
- 可用 MCP server 和 app connector。
- 已启用的 skills 和插件。
- 记忆、引用、上下文片段。
- 如果启用了计划模式或 review 模式，还会加入相应协作模式说明。

这一步的业务目标是：让模型既有足够信息完成任务，又不会拿到不该拿的能力或过多噪声。

### 3.6 暴露工具

核心层不会把所有工具无条件交给模型。本轮可用工具是根据配置、权限、输入内容和外部连接动态计算的。

例如：

- shell 工具是否可用，取决于配置、沙箱和执行策略。
- MCP 工具是否可用，取决于 MCP server 是否启动成功。
- app connector 工具是否可用，取决于用户是否 mention、app 是否启用、是否可访问。
- dynamic tool 是否可见，取决于 thread/start 或历史中注册的工具。
- 某些工具可能只在 tool search 后才暴露。
- 某些工具可能只给 code mode 内部使用，不直接给模型普通调用。

业务上，这是“能力授权”和“能力发现”的结合。

### 3.7 发起模型采样

核心层把整理后的输入、工具规格、模型配置、trace 信息、token metadata 发给模型 provider。

模型通常以流式方式返回事件。核心层边接收边处理：

- 有文字 delta，就通知 UI 展示。
- 有推理摘要 delta，就通知 UI 展示或记录。
- 有工具调用，就准备执行。
- 有 rate limit 信息，就更新状态。
- 有完成事件，就判断本轮是否结束。

这一步不是一次性请求响应，而是持续处理一个事件流。

## 4. 工具调用的业务闭环

Agent 的核心能力来自“模型思考”和“工具执行”的循环。模型不能自己改文件、跑命令、访问 MCP，它只能请求工具。核心层负责把请求变成真实动作。

### 4.1 识别工具请求

当模型输出一个工具调用时，核心层会判断：

- 这个工具名是否存在。
- 它是内置工具、shell 工具、MCP 工具、dynamic tool、web search、image generation，还是 app connector。
- 参数是否能解析。
- 是否支持并行执行。
- 是否要展示参数增量。

如果工具不存在或参数错误，核心层会把错误作为工具结果回传给模型，让模型有机会修正。

### 4.2 权限和审批判断

工具执行前，核心层要判断副作用风险：

- 会不会读写文件。
- 是否会访问网络。
- 是否会运行 shell 命令。
- 是否需要突破当前沙箱。
- 是否匹配已批准的命令前缀或网络规则。
- 是否必须询问用户。
- 是否可以自动批准。
- 是否被策略拒绝。

如果需要用户决定，核心层发出审批事件。上层界面展示给用户。用户的选择再作为操作回到核心层。

审批不是 UI 的附属功能，而是核心业务逻辑的一部分。因为真正知道工具风险和当前权限状态的是核心层。

### 4.3 执行工具

批准后，核心层执行工具。不同工具有不同执行方式：

- shell 命令进入统一执行路径，受沙箱、权限 profile、网络策略、超时和输出截断约束。
- MCP 工具通过对应 MCP server 的连接执行。
- dynamic tool 可能发回给客户端，由客户端执行后响应。
- web search、image generation、tool search 有各自的协议和结果格式。
- patch/file edit 类能力会记录文件变化。

执行过程中，核心层会持续发事件，例如命令开始、输出增量、完成、失败。

### 4.4 把工具结果反馈给模型

工具执行完后，核心层会把结果转换成模型可理解的输入项：

- exit code。
- stdout/stderr 摘要。
- 执行耗时。
- 截断提示。
- MCP 返回内容。
- 文件变更摘要。
- 错误信息。

然后核心层会再次调用模型，让模型基于工具结果继续推理。

这就是 agent 的循环：

```text
用户目标
-> 模型判断下一步
-> 工具执行
-> 工具结果回给模型
-> 模型继续判断
-> 直到最终回答或停止
```

## 5. Turn 如何结束

一个 turn 可能以几种方式结束。

### 正常完成

模型给出最终回答，并且没有要求继续工具调用。核心层会：

- 标记 turn completed。
- 更新 token usage。
- 发出最终消息。
- 保存历史。
- 刷新状态。
- 通知上层可以恢复输入。

### 需要继续采样

如果模型响应表示还没结束，或者工具调用完成后需要继续，核心层会再次发起模型请求。

这对用户来说仍然是一个 turn，但内部可能经历多次模型请求。

### 用户中断

用户按 Esc 或上层发出 interrupt。核心层会：

- 取消当前任务。
- 终止或清理相关后台进程。
- 记录中断 marker。
- 通知 UI turn aborted。
- 保留已完成的历史项。

这让用户可以停止长时间运行的 agent，同时保留已经发生的事实。

### 审批拒绝

用户拒绝命令或文件修改后，核心层会把拒绝结果反馈给模型。模型可以选择：

- 换一种方案。
- 解释无法继续。
- 请求其他权限。

拒绝不一定导致 turn 结束，它是模型下一步决策的输入。

### 错误失败

模型请求失败、工具执行失败、上下文超限、配置无效、MCP 失败等都可能导致错误事件。核心层会区分：

- 可重试错误：例如流式连接断开，可以重试或从 WebSocket fallback 到 HTTPS。
- 不可重试错误：直接失败并通知上层。
- 工具级错误：反馈给模型，让模型调整。
- 会话级错误：终止当前 turn。

## 6. 历史和上下文管理

核心层必须解决一个困难问题：历史越来越长，但模型上下文有限。

它的业务策略包括：

- 保存完整过程，便于审计和恢复。
- 构造模型输入时，只选择当前模型需要的历史。
- 在必要时触发 compact，把长历史压缩成更短摘要。
- 对 fork、resume、rollback 做历史重建。
- 对被中断的 turn 插入明确标记，避免恢复时误以为它正常完成。
- 对工具输出做截断，避免大输出挤爆上下文。

也就是说，持久化历史和模型可见历史不是同一件事：

- 持久化历史追求完整、可恢复。
- 模型可见历史追求足够、相关、可放入上下文窗口。

## 7. 配置如何影响业务逻辑

核心层每次运行都受到配置影响。配置不是静态背景，而是业务决策输入。

常见影响包括：

- 选择哪个模型。
- 使用哪家 provider。
- 是否允许联网。
- shell 是否运行在沙箱中。
- 文件系统哪些目录可读写。
- 什么时候需要审批。
- 是否启用 MCP。
- 是否启用 skills、plugins、apps。
- 是否启用多 agent。
- 是否使用某种 collaboration mode。
- 是否允许记忆或外部上下文污染记忆。

并且配置可能被管理策略约束。用户传入的选项不一定最终生效，核心层会解析成“实际生效配置”，并在必要时发出警告或拒绝请求。

## 8. MCP 在核心层里的角色

MCP 是外部工具生态的连接层。核心层把 MCP server 当成可启动、可查询、可调用、可失败的外部能力集合。

核心层对 MCP 做的业务工作包括：

- 根据配置启动 MCP server。
- 跟踪每个 server 的启动状态。
- 聚合 server 提供的 tools、resources、templates。
- 把 MCP tool 转成模型可见工具。
- 调用具体 MCP tool。
- 处理 MCP server 发起的 elicitation，也就是 server 反过来请求用户决策或输入。
- 在 session 结束时关闭 MCP 连接和子进程。

MCP 的失败不一定导致整个 agent 失败。某个 server 失败时，核心层可以继续运行，只是相关工具不可用，并把状态通知给界面。

## 9. Skills、AGENTS.md、Plugins 在核心层里的角色

这三者都影响模型“应该怎么做”，但定位不同。

### AGENTS.md

AGENTS.md 是项目本地规则。核心层会按工作目录读取相关规则，把它们注入给模型。

它回答的是：“在这个仓库里工作时要遵守什么约定？”

### Skills

Skill 是可复用的方法说明或流程能力。用户可以显式引用 skill，也可能由系统根据命令隐式触发。

它回答的是：“面对这类任务，应该按什么专门流程做？”

### Plugins

Plugin 可以贡献 skills、apps/connectors 或 marketplace 能力。

它回答的是：“系统外部安装了哪些可扩展能力？”

核心层会把这三者合并到本轮上下文和工具发现中，但不会把它们混为一种东西。

## 10. 多 Agent 的业务逻辑

多 agent 并不是简单地“同时问几个模型”。在核心层里，每个 sub-agent 都是一个独立 thread，只是它带有父子关系和 agent 元数据。

多 agent 业务流程通常是：

1. 主 agent 判断某个子任务可以委派。
2. 核心层检查是否超过最大 agent 数或最大深度。
3. 创建子 thread。
4. 子 thread 继承必要上下文，例如部分历史、shell snapshot、执行策略。
5. 子 agent 独立运行自己的 turn。
6. 主 agent 可以等待、发送消息、关闭或读取子 agent 状态。
7. 子 agent 的结果通过 mailbox 或事件回到主 agent。

这样做的好处是：

- 子任务有独立历史和状态。
- 子 agent 可以并行执行。
- 父子关系可追踪。
- 子 agent 的失败不必污染主 thread 的完整状态。
- 可以控制深度和数量，避免无限扩张。

## 11. 目标、记忆和长期状态

核心层还支持一些跨 turn 的长期业务状态。

### Goal

Goal 是 thread 级目标。它可以有状态、token budget、暂停/继续逻辑。核心层会根据 goal runtime event 决定是否在空闲时继续推进。

它解决的是“这个 thread 当前到底还在追什么目标”的问题。

### Memory

Memory 用于把有价值的长期信息纳入后续上下文。但核心层也会标记某些外部上下文可能污染 memory，例如 web search 或外部工具结果。

它解决的是“哪些内容值得带到以后，哪些内容不应该长期记住”的问题。

### Thread metadata

Thread 还可能持有名字、git 信息、memory mode、dynamic tools、source 等元数据。这些信息影响列表、恢复、过滤、归档和 UI 展示。

## 12. 核心层如何与上层界面协作

核心层不直接决定界面怎么画，但它会通过事件表达业务状态。

典型事件包括：

- 会话配置完成。
- turn 开始。
- item 开始。
- agent 消息增量。
- reasoning 增量。
- 工具调用开始。
- 工具输出增量。
- 工具调用完成。
- 审批请求。
- MCP 启动状态。
- token usage。
- 文件 diff。
- turn 完成。
- turn 中断。
- 错误和警告。

上层界面的职责是把这些事件变成用户能理解的交互。核心层的职责是保证这些事件语义准确、顺序合理、可持久化。

## 13. 不同用户场景下的核心层处理方式

### 只聊天，不需要工具

核心层仍然会创建 turn、构造上下文、调用模型、流式返回文本、保存历史。只是模型没有发起工具调用，turn 很快正常完成。

### 让 agent 修改代码

核心层会暴露 shell、patch、文件相关工具。模型通常先读文件或搜索，再修改，再运行测试。每个副作用都会经过权限和审批判断，并被记录成 item。

### 命令需要更高权限

核心层不会直接执行失败命令的升级版本。它会发出审批或权限请求，说明命令、原因、可能的额外权限。用户批准后才继续。

### 命令输出太大

核心层会保留执行结果，但给模型的内容会截断并带上截断提示，避免上下文被日志淹没。

### MCP server 没启动成功

核心层会通知启动失败。相关 MCP 工具不会暴露或调用。模型仍可使用其他能力继续。

### 用户中途补充要求

如果当前 turn 可 steer，补充输入会进入 active turn。否则会排队或触发新 turn。核心层会避免把补充输入误塞进不可 steering 的 review/compact turn。

### 用户拒绝审批

拒绝会被记录并反馈给模型。模型应调整方案。核心层不会偷偷绕过用户决定。

### 上下文太长

核心层可能发起 compact，或在构造 prompt 时选择压缩后的历史。用户看到的是会话继续，但模型看到的是更短、更聚焦的上下文。

### 恢复旧会话

核心层从持久化记录中重建 thread 状态、历史、配置快照和必要 metadata。被中断的 turn 会带中断标记，避免把半截输出当作正常结论。

### Fork 会话

核心层复制或截取原 thread 历史，创建新 thread。新 thread 与原 thread 分开演进，但保留来源关系。

### 多 agent 并行

核心层把子 agent 当独立 thread 管理。主 agent 负责委派和汇总，核心层负责资源限制、状态追踪和通信通道。

## 14. 核心层的业务边界

核心层应该做：

- 决定 agent 运行流程。
- 管理 turn 生命周期。
- 管理模型上下文。
- 管理工具可见性和调用。
- 执行权限、安全、审批判断。
- 管理 MCP、skills、plugins 对本轮的影响。
- 记录和恢复历史。
- 发出准确事件。

核心层不应该做：

- 直接画 UI。
- 把产品入口逻辑写进业务循环。
- 绕过 app-server 协议随意给客户端加私有行为。
- 让工具直接越过权限系统执行副作用。
- 把所有新能力都塞进 `codex-core`。
- 把持久化历史和模型可见上下文混为一谈。

## 15. 用一句话理解核心 Agent 层

核心 agent 层不是“模型调用器”，而是一个带状态、权限、工具、历史和事件流的任务执行系统。

它把用户目标转化为一个可控的执行闭环：

```text
接收目标
-> 准备上下文
-> 暴露能力
-> 调用模型
-> 执行工具
-> 处理审批和风险
-> 回灌结果
-> 继续推理或结束
-> 保存过程
-> 通知界面
```

理解这个闭环后，再看具体代码会清楚很多：每个模块其实都在服务闭环中的某一环，而不是零散的工程工具。
